### Checks against the brief (all other items found sound)

- **Mandated rules.** Every tool call goes through `GuardrailWrapper.call` (only the wrapper calls `prepare().run`). `createMcpServer` is the only entry for `tools/call`. `defineTool` is branded and `ToolRegistry` refuses unbranded tools. There is no tool or route that issues an approval, and `registry.test.ts` enumerates the real tools. A write without a valid approval never reaches its handler. Named tests exist for refused writes (wrapper.test.ts), one audit record per call (wrapper.test.ts, plus the 5-client concurrency spec) and rate-limit rejection (the 31st read and 4th write). The redactor is applied to audit inputs and to every log line.
- **Approval design.** There is no approval code. Confirmation reads `/dev/tty` and `approve` refuses to run without a terminal. State machine: claim is synchronous (approved to executing), `release` on intent failure and `consume` after the intent line is written. Binding is to tool, client and the SHA-256 of the canonical inputs. The window is 5 minutes from approval, inclusive. The socket directory check covers symlink, owner and group/world bits, and the socket is mode 0600. The accepted risk (same-user shell) is stated in README.md and the security design.
- **Audit ordering.** The intent line is fsynced (`durable`) before `consume` and `execute`. The outcome line follows. The sink has a lock file and a 100 MiB cap that marks the file unwritable instead of truncating it.
- **HTTP mode.** It binds 127.0.0.1, checks Host and then Origin before the token, compares SHA-256 hashes with `timingSafeEqual` over every token, serialises failed logins in a queue (200 ms, 20 waiting), caps the body at 64 KiB (declared and streamed) and the connections at 50.
- **Prompt injection.** The snapshot log excerpt and the advisory summary are sanitised and covered by tests that put instruction-like text through the tools. Live-mode metadata fields are the exception (R-01).
- **README accuracy.** The commands, scripts, variables and defaults match `package.json`, `config.ts` and the code. The README never claims a stdio size refusal. The only mismatch with behaviour is the mode shown by `approve` (R-03).
- **code-summary.md claims.** Confirmed: 494 tests, the guardrail coverage numbers, the overall coverage figures, the clean tsc, ESLint and Prettier results, and that nothing was committed (git status shows all new files untracked). Not confirmable here: "stable over repeated runs", the benchmark numbers and the single walkthrough run. The "Not verified here" section is honest about workflows, gitleaks and repository settings.
- **source-manifest.json.** The path list covers every created root file and directory (`src/`, `test/`, `snapshots/`, `.github/`, `scripts/` and the root config files). `.prettierignore` is listed too. No missing entry found.

### Summary

The guardrail core (wrapper, approval, audit, rate limiter, admin channel) matches the approved design, and I could not break it: coverage is 100% on `src/guardrails/**`, the thresholds are intact, and the type check, lint and format checks are clean. The two blocking-class gaps are that live-mode job, step and workflow names bypass the untrusted-text sanitiser (R-01) and that the stdio 64 KiB limit silently drops oversize messages and has no test (R-02). Neither can bypass approval. With two Major findings and no Critical ones, the verdict is READY, and both should be fixed in the next pass.
